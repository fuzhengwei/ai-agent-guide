第28章 Jev 决策模型：Agent 的"反射神经"

不写字、只做判断——System One 决策模型与 Agent 的快慢分工

📍 这一章怎么读

2026 年 9 月 15 日，前 OpenAI 研究员、RLHF 发明人之一 Diogo Almeida 创办的 TypeSafe AI 发布了 Jev——一个不生成任何文字、只输出"带概率的结构化判定"的模型。它在开发者圈刷屏的原因不是"更强"，而是更专：把 Agent 运行中最高频的分类、路由、评分、真伪判断，从昂贵的 LLM 调用中剥离出来。

小白路线：先看 28.1 理解"Agent 每一步都在做选择题"，再看 28.2 的三种输出类型，建立直觉。

开发路线：重点看 28.3（单 Token Logits 直判机制）、27.5（快慢分工架构）和 28.6（APUS 开源复现），这些是可以直接落地的工程方案。

面试路线：27.2 的三种输出类型、27.4 的 RLCD 校准训练、27.5 的 System 1/System 2 分工是高频考点。

28.1 为什么需要决策模型

先看一个真实的 Agent 运行账单。一个客服 Agent 处理一个用户请求，Loop 大概跑 8 轮：

# 一个客服 Agent 处理 1 个工单的真实 LLM 调用
第1轮: 理解用户意图           → AI-5 生成 300 token 分析   💰💰
第2轮: 判断"该调哪个工具？"    → AI-5 生成 200 token 推理   💰💰  ← 其实只是个选择题
第3轮: 判断"要升级人工吗？"    → AI-5 生成 150 token 推理   💰💰  ← 其实只是个是非题
第4轮: 判断"这个API调用安全吗" → AI-5 生成 180 token 推理   💰💰  ← 其实只是个是非题
第5轮: 给工单打优先级          → AI-5 生成 120 token 推理   💰💰  ← 其实只是个评分题
第6轮: 起草回复               → AI-5 生成 800 token 回复   💰💰
第7轮: 校验自己的回复是否合规   → AI-5 生成 200 token 检查   💰💰  ← 其实只是个是非题
第8轮: 决定"任务完成了吗"      → AI-5 生成 100 token 总结   💰💰  ← 其实只是个是非题

8 次调用中，5 次的最终答案只是"选A/选B"、"是/否"、"3分"
但为了这 5 个原子判断，模型生成了 750+ token 的"思考过程"

这就是 Diogo Almeida 在 OpenAI 时就想不通的问题：

🔥 创始人的原话

"我们花了四年把模型的人类语言能力优化到极致，但这对自动化没用——计算机说的不是人类语言。软件需要的是一个决定，不是一段散文。"

28.1.1 Agent 的决策瀑布

Agent 每跑一轮 Loop，背后隐藏着大量"看不见的判断"。把这些判断全部交给 LLM 逐字生成，就像让一位博士去按电梯按钮——能力溢出、成本高、还慢：

💡 关键矛盾

Agent 越成熟，"快判断"的调用量越大（每一步都要路由、校验、打分），而这些判断延迟敏感、频次极高、答案空间极小。用生成式 LLM 做这件事，等于把"从 4 个按钮里按 1 个"变成"写一篇 200 字议论文再从中解析出按钮编号"——既贵又慢，还可能解析出错（格式幻觉）。

28.1.2 杰文斯悖论：为什么叫 Jev

Jev 的名字来自 19 世纪经济学家威廉·斯坦利·杰文斯（William Stanley Jevons）。他在《煤炭问题》中提出著名的杰文斯悖论：蒸汽机效率提升、煤炭使用成本下降，结果不是煤炭用量减少，而是总消耗量暴涨——因为便宜的煤炭催生了无数新用途。

📌 命名背后的赌注

TypeSafe 押注：智能判断的成本暴跌 → 智能判断的用量暴涨。

当一次判断只要 0.1 毫秒级成本、免费输出时，开发者会把"以前舍不得用 AI 的地方"全部 AI 化：每一条日志的分类、每一次按钮点击的意图、每一个 API 调用的安检……智能从"对话界面"变成"软件基础设施"，像水电一样无处不在。这也是微软 CEO 纳德拉多次引用杰文斯悖论描述 AI 浪潮的原因。

28.2 Jev 是什么：三种输出，不生成一个字

Jev 被 TypeSafe 定义为第一个 System One 模型——名字来自心理学家卡尼曼《思考，快与慢》中的双系统理论：

维度 System 2（慢思考） System 1（快思考）
人类类比解数学题、写论文直觉、条件反射、一眼判断
对应模型AI / Claude / DeepSeek 等 LLMJev 决策模型
输出形式逐 token 生成文本带概率的结构化判定
延迟秒级70–500 毫秒
适合任务规划、推理、生成、解释分类、路由、评分、真伪校验
调用频次低（每个任务几次）高（每个任务几十上百次）

28.2.1 请求范式：state + questions

调用 Jev 不是发一段 prompt 等它"回答"，而是提交一个状态（state）和一组预先定义好答案空间的问题（questions）。所有问题针对同一个 state 并行评估，互不干扰：

POST https://api.typesafe.ai/v1/systemone
{
  "model": "jev-1.13.0",
  "state": "用户消息：你们这个破系统又扣错费了！第三次了！我要投诉！",
  "questions": {
    "route":    { "type": "choice", "criteria": { "billing": "扣费/账单相关", "tech": "功能故障", "sales": "商务咨询" } },
    "priority": { "type": "score",  "criteria": ["低", "中", "高", "紧急"] },
    "refund":   { "type": "noul",   "instructions": "用户明确要求退款" }
  }
}

# 响应（约 100ms，输出免费）
{
  "route":    { "choice": "billing", "probabilities": {...}, "confidence": 0.94 },
  "priority": { "score": 3.7, "probabilities": {...}, "confidence": 0.88 },
  "refund":   { "noul": 0.31 }
}

28.2.2 三种输出类型（背下来，必考）

类型 适用场景 定义方式 返回内容
choice 选择 答案是一组无序选项之一（意图分类、工单路由、文档类型） criteria：选项 → 描述的映射，最多 255 个选项 选中的 choice + 每个选项的概率 + confidence
score 评分 答案在有序刻度上（严重度、沮丧度、质量分） criteria：有序等级描述，2–10 级 score（可落在等级之间）+ legend + 概率 + confidence
noul 真伪概率 干净的是/非判断（"这条 API 调用危险吗"） instructions + 可选的 true/false 含义描述 0（否）到 1（是）的概率值，无 confidence 字段
🔤 冷知识：noul 是什么词？

noul 是 Bernoulli（伯努利） 的缩写——伯努利分布就是"结果只有是/否两种"的概率分布。TypeSafe CEO 在 Hacker News 上确认了这个命名（Vercel AI SDK 里叫 boolean）。面试时说出这个典故，直接加分。

28.2.3 为什么说它"不会幻觉"

注意措辞：Jev 不是"不会判断错"，而是不可能产生格式幻觉。传统 LLM 做分类任务时，你要先让它生成文本，再用正则/JSON 解析提取答案——模型可能输出"我觉得应该是 billing，不过也有可能……"，解析直接崩掉。Jev 的输出空间在请求时就被锁死：

✅ 类型安全（Type-Safe）的两层含义

① 结构上不会错：采样只在你定义的答案空间内进行，返回的一定是合法选项/合法分值/0-1 概率，永远不会是自由文本。
② 概率上可信赖：输出附带校准过的置信度，你可以直接写 if (confidence > 0.9) 自动执行; else 升级给 LLM 这样的业务逻辑——这是普通分类头做不到的（见 28.4）。

28.3 底层机制：跳过自回归，隐状态直接打分

Jev 为什么能快 40–200 倍？TypeSafe 没公开完整架构（外界普遍猜测是基于某个开源权重模型改造），但从其文档展示的输入范式和 APUS 的开源复现中，可以还原出核心机制：

28.3.1 单 Token Logits 直判

关键洞察：分类、评分、是非判断的答案空间极小（255 个选项、10 个等级、是/否），一个 token 的 logits 就足够编码整个答案分布。传统做法是"生成很多 token 再从中找答案"，Jev 的做法是：

# 传统 LLM 做分类（自回归，逐 token 生成）
输入: "...这条消息该分到哪类？"
生成: "根" → "据" → "分" → "析" → ... → "billing"   # 几十个 token，几十次前向

# Jev / 决策模型（单次前向，logits 直读）
输入: state + 问题定义
一次前向计算 → 取答案空间对应位置的 logits → softmax → 概率分布
             → billing: 0.94, tech: 0.05, sales: 0.01            # 1 次前向搞定

28.3.2 KV-Cache 广播 + 并发批量评估

一次请求里的多个问题共享同一个 state。Jev 把 state 的 KV-Cache 广播给所有问题并行复用——state 只编码一次，13 个问题和 1 个问题的成本几乎相同：

调用方式 成本 速度
13 个问题分 13 次调用（串行）基准基准
13 个问题合并 1 次请求（KV-Cache 广播）便宜 12.2 倍快 10 倍
⚠️ 工程启示：把问题打包

这个特性直接影响你的 Agent 设计：同一状态下的所有判断应该聚合到一次请求中。比如"路由 + 优先级 + 是否升级人工"三个判断，打包成一次调用，成本只有分开调用的 1/12。设计 Agent Loop 时，把判断点尽量集中到一个"决策步骤"，而不是散落在各环节。

28.4 RLCD：为"校准"而生的训练方法

Jev 全程使用合成数据训练，训练方法叫 RLCD（Reinforcement Learning for Calibrated Decisions，校准决策强化学习）。它和你熟悉的 RLHF 有本质区别：

维度 RLHF（训练 AI 聊天助手） RLCD（训练 Jev）
奖励目标人类偏好的回答（好听、有用）准确且校准的判断（概率 = 真实频率）
输出形态自由文本结构化判定 + 置信度
"自信"的含义语气坚定（无统计意义）输出 0.9 → 真实准确率 ≈ 90%（有统计意义）
训练数据人类标注排序全合成数据

28.4.1 什么是"校准"（Calibration）

📌 校准的定义

模型说"我有 90% 把握"的所有判断里，真的大约 90% 是对的——预测概率与经验频率一致。

普通分类模型的 softmax 输出没有这个性质：它们普遍过度自信（输出 0.95 实际只对 70%）。未校准的概率不能写进业务逻辑，校准过的可以。

28.4.2 校准为什么值钱：置信度闸门

校准概率让一种全新的工程模式成为可能——置信度闸门（Confidence Gate）：

// 只有校准过的概率，才敢这么写
const { choice, confidence } = await jev.decide({ state, questions });

if (confidence > 0.9) {
  executeDirectly(choice);      // 90%+ 把握：自动执行，零人工零 LLM
} else if (confidence > 0.6) {
  executeWithLog(choice);       // 中等把握：执行但记录审计日志
} else {
  escalateToLLM(state);         // 没把握：升级给 System 2 大模型慢思考
}

这就是"快慢分工"能落地的技术前提：不是盲目信任小模型，而是用校准概率精确控制"什么时候该请大模型出山"。不确定的少数 case 交给 LLM，确定的大多数 case 用 Jev 毫秒级解决——整体成本降一个数量级，准确率几乎不掉。

28.4.3 校准 vs MDP：一个更深的视角

🧠 进阶理解（面试加分项）

严格说 Agent 面对的是 POMDP（部分可观测马尔可夫决策过程）：LLM 把历史压缩成高维上下文向量时必然丢信息，所以模型的输出本质上是一个信念状态（belief state），而不是对世界的确定认知。RLCD 做的事，就是把这个信念"校准"成可行动的概率——承认不确定，并把不确定量化。这比"假装确定"的传统分类头更适合做自动化决策。

28.5 快慢分工：LLM 写字、Jev 判断、代码执行

Jev 不是来取代 LLM 的。TypeSafe 官方给出的系统范式是三层结构：

28.5.1 典型落地场景

场景 System 2（LLM）做什么 System 1（Jev）做什么
客服 Agent理解对话、起草回复工单路由、优先级评分、是否升级人工
浏览器自动化理解任务目标、规划步骤每一步"点哪个元素"的原子决策
代码 Agent写代码、设计架构这个 API 调用安全吗 / 这段 diff 需要人工 review 吗
内容审核疑难 case 的深度分析海量内容的首道分类与风险评分
LLM 输出校验生成内容校验另一个 LLM 的输出是否合规（模型互查）

28.5.2 与 Harness 的关系

回忆第10章：Harness 是"模型外面的整套工程外壳"，负责组装与调度。Jev 恰好卡在 Harness 的决策层——Harness 里的路由规则、权限决策引擎（shouldUseSandbox）、重试策略，以前要么写死规则、要么调 LLM，现在有了第三个选项：校准决策模型。

✅ 一句话总结

过去的 Agent 架构是"LLM + if-else"，Jev 验证的新架构是"LLM 负责慢思考 + 决策模型负责快判断 + Harness 负责调度分工"。负责组装这套分工的工程层，就是 Harness。

28.6 国内动态：APUS 的开源复现 fast-browser-use

Jev 发布仅 4 天后（2026 年 9 月 19 日），中国 AI 企业 APUS（麒麟合盛）旗下实验室公布了全球最早一批独立复现成果，包装成开箱即用的 Agent Skill fast-browser-use，MIT 协议开源（Jev 官方 API 当时未向中国大陆开放）。

28.6.1 复现了什么

机制 复现方式
单 Token Logits 直判跳过自回归解码，本地 Qwen3.5-9B 单次前向计算直接打分
KV-Cache 广播state 编码一次，候选动作集合并发批量评估
类型安全输出页面可交互元素整理为带编号候选集，模型只输出编号——机制上消除"生成错误选择器"的幻觉

28.6.2 对开发者的意义

🛠️ 决策模型可以自托管

fast-browser-use 证明了：决策模型范式不依赖闭源 API。一个 9B 量级的开源模型 + 单次前向直判改造，就能在浏览器自动化场景复现 Jev 的核心机制，且支持 macOS / Linux / Windows、无 GPU 也能跑。对数据敏感的团队，这意味着"快慢分工"可以完全私有化部署——System 2 用本地 DeepSeek/Qwen，System 1 用改造的小模型，零 API 成本。

⚠️ 自己复现时的要点

想在自己的模型上加决策头（如 ModernBERT + choice/score 头），训练上通常分两步：先交叉熵把准确率练上去，再用 Brier Loss + 温度缩放（Temperature Scaling） 做概率校准。没有校准这一步，你的"confidence"就只是 softmax 的过度自信输出，写不进置信度闸门。

28.7 局限与边界

TypeSafe 官方罕见地公开了 Jev 的弱点清单（面试常考"它的边界在哪"）：

弱点 说明与对策
数学与计数不擅长精确数值计算——精确逻辑永远留在代码里，别让模型算
日期排序、数字近似对"哪个日期更早""哪个数更大"类比较不可靠，交给代码
双重否定"不是不可以"这类语义容易判反，写问题时避免嵌套否定
长上下文"腐烂"state 过长时判断质量下降——过滤和裁剪要在客户端做，别把整页日志塞进去
对抗输入评估不可信内容时仍有提示注入风险（输出格式收窄了攻击面，但没消除）
CJK 语言中文/日文/韩文判断准确率低于英文——中文场景建议充分自测或考虑本地复现方案
不能做的事不会写、不会解释、不会总结、不能跑代码 Agent——它只做判断
💡 架构原则：各司其职

Jev 的边界恰好印证了整个教程反复强调的原则：精确的留给代码，判断的留给决策模型，创造的留给 LLM。三者不是竞争关系，是同一条流水线上下游的工友。

📋 八股总结 — 面试高频考点
Q1: Jev 是什么？和传统 LLM 的本质区别是什么？
Jev 是 TypeSafe AI（2026-09-15 发布）的"System One"决策模型：输入 state + 预定义答案空间的 questions，单次前向计算直接输出带概率的结构化判定（choice/score/noul），不生成任何文本。

本质区别在三点：① 输出形式——LLM 逐 token 自回归生成文本，Jev 跳过自回归、隐状态直接打分；② 训练目标——LLM 用 RLHF 优化"人类偏好"，Jev 用 RLCD 优化"校准的判断"；③ 定位——LLM 是通用生成器，Jev 是 Agent 架构中专做高频原子判断的组件。

面试要点：强调"它不是更小的 LLM，而是不同物种"——架构有共同技术根源（Transformer 预训练），但输出格式和训练目标完全不同。
Q2: System 1 / System 2 分工是什么？为什么需要它？
借自卡尼曼双系统理论：System 2（LLM）负责慢思考——规划、推理、生成；System 1（决策模型）负责快判断——分类、路由、评分、校验。

需要它的原因：Agent 成熟后，高频小判断的调用量远超生成调用（一次任务几十上百次路由/校验 vs 几次生成），而这些判断延迟敏感、答案空间极小。全部用 LLM 做等于"写 200 字议论文再解析出一个按钮编号"——贵、慢、还有格式幻觉风险。快慢分工让整体成本降一个数量级，准确率几乎不掉。
Q3: Jev 的三种输出类型分别是什么？各自适用场景？
① choice：无序选项分类（最多 255 个），用于意图识别、工单路由。返回选中项 + 全选项概率 + confidence。
② score：有序刻度评分（2-10 级），用于严重度/质量打分。返回分数（可在等级之间）+ legend + 概率 + confidence。
③ noul：是/非概率（Bernoulli 缩写），用于安全闸、真伪校验。返回 0-1 概率，没有 confidence 字段。

面试要点：能说出"noul = Bernoulli 缩写"是加分项；能指出"noul 无 confidence 字段"说明你读过 API 文档而不是只看了新闻。
Q4: 什么是 RLCD？校准（Calibration）为什么重要？
RLCD（Reinforcement Learning for Calibrated Decisions）：Jev 的训练方法，用全合成数据训练，奖励目标是"预测概率与真实频率一致"——模型输出 0.9 时，这批判断真实准确率约 90%。

校准的价值在于置信度闸门：普通分类头的 softmax 输出普遍过度自信（输出 0.95 实际对 70%），不能写进业务逻辑；校准后的概率可以直接写 if confidence > 0.9 自动执行，else 升级 LLM。这是快慢分工能落地的技术前提——用概率精确控制"什么时候请大模型出山"。

面试加分：自己实现时，先交叉熵练准确率，再用 Brier Loss + 温度缩放做校准。
Q5: Jev 为什么快？核心机制是什么？
两个核心机制：
① 单 Token Logits 直判：决策任务答案空间极小（255 选项/10 等级/是非），一个 token 的 logits 足够编码整个答案分布。跳过自回归解码，一次前向计算直接读答案空间的 logits 做 softmax——从"几十次前向生成文本再解析"变成"一次前向出概率"。
② KV-Cache 广播 + 并发批量评估：同一 state 编码一次，多个问题共享 KV-Cache 并行评估。13 个问题合并一次请求比串行便宜 12.2 倍、快 10 倍。

面试要点：性能数据要说典型区间（快 40-200×、便宜 40-400×），并指出 193.6×/444.6× 是厂商峰值口径——这是区分"读过分析"和"只看了标题"的细节。
Q6: Jev 说"不会幻觉"，准确吗？
准确的说法是"不可能产生格式幻觉"，不是"不会判断错"。

传统 LLM 做分类要先生成文本再解析，可能输出"我觉得是 billing 但也可能……"导致解析失败。Jev 的采样被锁死在预定义的答案空间内，返回的一定是合法选项/分值/概率，结构上永远合法（这就是 Type-Safe 的双关）。但判断内容本身可能错——只是它用校准概率把"我可能错"量化了，让你可以用置信度闸门处理。
Q7: Jev 有哪些已知局限？工程上如何应对？
官方公开的弱点：数学/计数、日期排序、数字近似、双重否定、长上下文腐烂、对抗输入、CJK 语言准确率偏低。

应对原则：精确的留给代码，判断的留给决策模型，创造的留给 LLM。数值计算和日期比较写代码；长 state 在客户端先过滤裁剪再提交；问题措辞避免嵌套否定；中文场景充分自测或考虑本地复现（如 APUS fast-browser-use，9B 开源模型 + 单 token 直判改造，可私有化部署）。
Q8: Jev 和 Harness 是什么关系？在 Agent 架构里处于什么位置？
Jev 卡在 Harness 的决策层。Harness 里的路由规则、权限决策（如 Claude Code 的 shouldUseSandbox）、重试策略，过去只有两种实现：写死规则（不灵活）或调 LLM（贵且慢）。决策模型提供了第三条路：校准过的毫秒级判断。

完整架构是三层：LLM 负责慢思考 + 决策模型负责快判断 + Harness/代码负责调度与执行。这验证了 Harness 工程的核心观点——Agent 性能的变量在模型外面的工程体系，而不是模型本身。Jev 本身就是"换一种模型嵌入 Harness"的产物：它没有取代任何模型，而是重新定义了模型之间的分工界面。
