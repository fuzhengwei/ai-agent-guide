第5章 上下文工程：给 LLM 发送的内容

从"塞进去就行"到"精准投放"——Agent 大脑的输入管理

📍 这一章怎么读

提示词工程关注怎么写一条好的指令，上下文工程关注每次调用时往上下文窗口里放什么。LLM 的上下文窗口是有限的（4K-200K token），而 Agent 多轮对话、工具返回、记忆检索的内容会不断膨胀。如何取舍、如何压缩、如何保证关键信息不丢失——这就是上下文工程要解决的核心问题。

小白路线：先看 5.1 理解"上下文窗口 = Agent 的工作台"，再看 5.2 的五种裁剪策略动画，建立直觉。

开发路线：重点看 5.3（消息优先级分级）、5.4（混合裁剪）、5.6（Claude Code 三级压缩链），这些是生产环境真正在用的工程方案。

面试路线：5.2 的五种策略对比、5.4 的混合裁剪设计、5.5 的上下文工程 vs 提示词工程关系是高频考点。

5.1 为什么需要上下文工程

上一章我们学了提示词工程——如何写出一条好的 System Prompt。但在 Agent 实际运行中，每次调用 LLM 时，发送的内容远不止一条提示词：

⚠️ Agent 每轮发送给 LLM 的内容

一次 Agent Loop 中，发给 LLM 的完整上下文通常包含：

  • System Prompt — 角色设定、行为规则、安全约束（固定，每轮都发）
  • 工具定义 — Function Calling 的 JSON Schema（固定，但占大量 token）
  • 对话历史 — 之前所有轮次的 user/assistant/tool 消息（持续增长）
  • 工具返回值 — 搜索结果、代码执行输出、API 响应（可能非常长）
  • 记忆注入 — 从长期记忆或 RAG 检索的相关内容（动态变化）
  • 当前用户输入 — 这一轮用户说的话（最不可省的部分）

这些内容加在一起，很容易超出模型的上下文窗口限制。

来看一个典型的 Token 膨胀过程：

# 第1轮：System Prompt + 用户提问
System: "你是一个助手..."  →  200 tokens
User: "帮我分析这段代码"     →   50 tokens
                           总计: 250 tokens ✅

# 第5轮：历史对话开始累积
System + 工具定义 + 5轮历史   →  4,000 tokens
User: "继续优化"              →     30 tokens
                           总计: 4,030 tokens ✅

# 第15轮：工具返回值大量堆积
System + 工具定义 + 15轮历史   →  20,000 tokens
Tool Result: 代码执行输出      →   8,000 tokens  ← 大头！
User: "再改改"                →     20 tokens
                           总计: 28,020 tokens ⚠️

# 第30轮：接近窗口上限
全部内容累加                   →  85,000 tokens
                           总计: 85,000 tokens 🔴 接近 128K 上限！

# 第35轮：超出窗口
全部内容累加                   →  150,000 tokens
                           总计: 150,000 tokens ❌ API 报错 context_length_exceeded
💡 一句话理解

提示词工程是"怎么写好一句话"，上下文工程是"每次调用时带哪些内容、丢哪些内容、怎么压缩"。前者关注单条指令的质量，后者关注整个对话窗口的信息管理。

上下文工程 vs 提示词工程

维度 提示词工程 上下文工程
关注点单条指令怎么写每次调用带什么内容
时间跨度一轮对话整个会话生命周期
核心问题怎么让 LLM 理解指令怎么让有限窗口装下关键信息
典型手段Few-shot、CoT、角色设定裁剪、压缩、优先级分级
衡量指标指令遵循度、输出质量Token 利用率、信息保留率
失败模式LLM 不按指令行事关键信息被丢掉、Token 超限

两者不是替代关系，而是互补关系：好的提示词工程让单轮指令更有效，好的上下文工程让多轮对话可持续。在实际 Agent 项目中，上下文工程的重要性甚至超过提示词工程——因为 Agent 跑 30 轮后，提示词写得好不好已经不重要了，重要的是关键约束有没有被裁掉。

5.2 五种消息裁剪策略

当上下文总量接近窗口上限时，必须裁剪——决定哪些内容保留、哪些丢弃。工业界经过多年实践，总结出五种主流策略，从简单到复杂：

🎯 策略全景：从粗暴到精细

下面五种策略不是"选一个"，而是可以组合使用的。实际生产系统通常采用"混合裁剪"——后面会详细讲。

策略 1：截断（Truncation）

做法：超过窗口上限时，直接丢弃最早的消息，只保留最近的 N 条。

[消息1] [消息2] [消息3] [消息4] [消息5] [消息6] [消息7] [消息8]
                                                    ↑
                                              窗口上限 5 条
        ← 丢弃 ────────→  [消息4] [消息5] [消息6] [消息7] [消息8]
  • 优点：实现成本为零，O(1) 复杂度
  • 缺点：不考虑内容重要性——用户第一轮设定的约束可能被丢掉
  • 代表实现：OpenAI ChatCompletion API 的 max_tokens 参数；大多数 LLM SDK 的默认行为

策略 2：摘要压缩（Summarization）

做法：用 LLM 对旧对话生成摘要，用摘要替代原始内容。

[消息1] [消息2] [消息3] [消息4]  →  LLM 摘要  →  [摘要: 用户要做X, 已完成Y, 关键约束Z]
                                                ↓
                          [摘要] [消息5] [消息6] [消息7] [消息8]
  • 优点：保留关键信息的"精华"，信息损失可控
  • 缺点：每次压缩消耗额外 token 和延迟；二次摘要有信息蒸馏的熵增问题
  • 代表实现：LangChain ConversationSummaryMemory

策略 3：滑动窗口（Sliding Window）

做法：维护一个固定大小的窗口，始终保留最近 N 轮完整对话，超出的自动淘汰。

第1轮  第2轮  第3轮  第4轮  第5轮  第6轮  第7轮
                                     │ 窗口大小 = 5 │
       ← 自动淘汰 ←                  ←  保留最近5轮 →
  • 优点：上下文长度恒定，Token 消耗可预测
  • 缺点：只考虑时间远近，不考虑重要性——可能丢掉关键决策但保留了无关闲聊
  • 代表实现：LangChain ConversationBufferWindowMemory
⚠️ 滑动窗口 vs 截断

两者看起来很像，区别在于语义：截断是"被动超限时砍尾部"，滑动窗口是"主动维护固定大小"。在工程实现上，滑动窗口通常按轮次而非消息条数来计算——因为一轮对话可能包含 user + assistant + tool_result 三条消息。

策略 4：选择性保留（Selective Retention）

做法：按消息类型分别设定保留策略——系统指令全量保留、用户偏好标记后保留、工具返回值压缩后保留、闲聊直接丢弃。

消息类型        │ 保留策略              │ 理由
────────────────┼───────────────────────┼──────────────
System Prompt   │ 全量保留              │ 绝对不能丢
工具定义(Schema)│ 全量保留              │ LLM 需要知道有哪些工具
用户偏好/约束   │ 标记后永久保留         │ "用Python"、"简洁风格"
工具返回值       │ 提取关键字段后保留     │ 8000行日志→关键错误3行
闲聊/寒暄        │ 直接丢弃              │ "你好"、"谢谢" 无信息量
推理过程         │ 摘要后保留            │ Thought可压缩,Action要留
  • 优点：信息密度最高，每个 token 都有价值
  • 缺点：需要额外的分类器或规则引擎来判断消息类型，实现复杂度较高
  • 代表实现：Claude Code 的消息分类器、Cursor 的上下文优先级系统

策略 5：语义保护型压缩（Semantic-Preserving）

做法：最先进的策略——锁定核心指令（System Prompt 不压缩），确保行动-结果完整性（工具调用与其返回值成对保留），只压缩中间推理过程。

原始对话:
┌──────────────────────────────────────────────────────┐
│ System: "你是代码助手..."              [🔒 不压缩]    │
│ User: "修复这个bug"                    [🔒 不压缩]    │
│ Assistant: "让我先看代码结构..."        [📝 摘要压缩]  │
│ Tool Call: read_file("app.py")        [🔒 保留]      │
│ Tool Result: "def app(): ..." (800行)  [📝 提取关键]  │
│ Assistant: "问题在第42行..."           [📝 摘要压缩]  │
│ Tool Call: edit_file("app.py", ...)   [🔒 保留]      │
│ Tool Result: "成功"                    [🔒 保留]      │
│ User: "再检查下测试"                   [🔒 不压缩]    │
└──────────────────────────────────────────────────────┘

压缩后:
┌──────────────────────────────────────────────────────┐
│ System: "你是代码助手..."              [🔒 原样]      │
│ User: "修复这个bug"                    [🔒 原样]      │
│ [摘要: 分析了app.py结构, 发现第42行bug]               │
│ Tool Call: read_file → edit_file      [🔒 保留行动]  │
│ [摘要: 第42行有空指针, 已修复]                         │
│ User: "再检查下测试"                   [🔒 原样]      │
└──────────────────────────────────────────────────────┘
  Token: 85,000 → 12,000 (压缩率 86%)
  • 优点：在压缩率和信息完整性之间取得最优平衡
  • 缺点：实现最复杂，需要精确识别消息间的因果依赖
  • 代表实现：Claude Code 的 microCompact（保留工具调用对，压缩中间推理）

五种策略对比

策略 压缩率 信息保留 实现复杂度 额外 Token 开销 适用场景
截断高差O(1)0简单 demo
摘要压缩中高中中高（调用 LLM）长对话

5.3 消息优先级裁剪

五种策略中最适合生产环境的是选择性保留和语义保护型压缩。两者的核心思想都是：不同类型的消息，重要性不同，裁剪时应该按优先级来。这就是"消息优先级裁剪"——工业级 Agent 系统的标准做法。

消息优先级分级

Agent 对话中的消息可以分为多个优先级层级：

优先级 消息类型 裁剪策略 理由
P0 🔴 永不裁剪 System Prompt、当前用户输入 全量保留 System Prompt 是行为准则；当前输入是本轮任务目标
P1 🟠 尽量保留 工具调用 Schema、用户初始约束 全量保留，超限时压缩 Schema 描述 没有 Schema LLM 无法调用工具；初始约束影响全程
P2 🟡 可压缩 工具返回值、Action-Observation 对 提取关键字段，丢弃原始大块输出 8000 行日志只需保留关键错误 3 行
P3 🔵 可摘要 中间推理过程（Thought） 摘要压缩，保留结论 "让我想想..." 的推理链可压缩为结论
P4 ⚪ 可丢弃 寒暄、确认、重复消息 直接丢弃 "好的"、"明白了" 无信息价值

优先级裁剪算法

当上下文总量超过预算时，裁剪按优先级从低到高执行：

def priority_based_prune(messages, token_budget):
    """
    按优先级裁剪消息列表，使总 token 不超过预算。
    messages: [{role, content, type, priority, tokens}]
    token_budget: 目标 token 上限
    """
    total = sum(m["tokens"] for m in messages)
    if total <= token_budget:
        return messages  # 不需要裁剪

    # P4: 先丢弃最低优先级的消息
    for m in messages:
        if m["priority"] == 4:
            m["_action"] = "drop"
            total -= m["tokens"]
            if total <= token_budget:
                return finalize(messages)

    # P3: 摘要压缩推理过程
    for m in messages:
        if m["priority"] == 3 and m["_action"] != "drop":
            summary_tokens = summarize(m["content"])
            m["_action"] = "summarize"
            m["_new_tokens"] = summary_tokens
            total = total - m["tokens"] + summary_tokens
            if total <= token_budget:
                return finalize(messages)

    # P2: 提取工具返回值关键字段
    for m in messages:
        if m["priority"] == 2 and m["_action"] != "drop":
            extracted = extract_key_fields(m["content"])
            m["_action"] = "extract"
            m["_new_tokens"] = len(extracted) // 4
            total = total - m["tokens"] + m["_new_tokens"]
            if total <= token_budget:
                return finalize(messages)

    # P1: 压缩工具 Schema 描述（保留结构，精简 description）
    for m in messages:
        if m["priority"] == 1 and m["_action"] != "drop":
            compressed = compress_schema(m["content"])
            m["_action"] = "compress_schema"
            m["_new_tokens"] = len(compressed) // 4
            total = total - m["tokens"] + m["_new_tokens"]

    # P0 永不裁剪
    return finalize(messages)


def finalize(messages):
    result = []
    for m in messages:
        if m.get("_action") == "drop":
            continue
        elif m.get("_action") == "summarize":
            result.append({**m, "content": summarize(m["content"])})
        elif m.get("_action") == "extract":
            result.append({**m, "content": extract_key_fields(m["content"])})
        elif m.get("_action") == "compress_schema":
            result.append({**m, "content": compress_schema(m["content"])})
        else:
            result.append(m)
    return result
interface Message {
  role: string;
  content: string;
  type: string;
  priority: 0 | 1 | 2 | 3 | 4;
  tokens: number;
  _action?: 'keep' | 'drop' | 'summarize' | 'extract' | 'compress_schema';
  _newTokens?: number;
}

function priorityBasedPrune(messages: Message[], tokenBudget: number): Message[] {
  let total = messages.reduce((sum, m) => sum + m.tokens, 0);
  if (total <= tokenBudget) return messages;

  // P4: 丢弃最低优先级
  for (const m of messages) {
    if (m.priority === 4) {
      m._action = 'drop';
      total -= m.tokens;
      if (total <= tokenBudget) return finalize(messages);
    }
  }

  // P3: 摘要压缩推理过程
  for (const m of messages) {
    if (m.priority === 3 && m._action !== 'drop') {
      m._action = 'summarize';
      m._newTokens = await summarize(m.content).length / 4;
      total = total - m.tokens + m._newTokens;
      if (total <= tokenBudget) return finalize(messages);
    }
  }

  // P2: 提取工具返回值关键字段
  for (const m of messages) {
    if (m.priority === 2 && m._action !== 'drop') {
      m._action = 'extract';
      m._newTokens = extractKeyFields(m.content).length / 4;
      total = total - m.tokens + m._newTokens;
      if (total <= tokenBudget) return finalize(messages);
    }
  }

  // P1: 压缩工具 Schema 描述
  for (const m of messages) {
    if (m.priority === 1 && m._action !== 'drop') {
      m._action = 'compress_schema';
      m._newTokens = compressSchema(m.content).length / 4;
      total = total - m.tokens + m._newTokens;
    }
  }

  return finalize(messages);
}

5.4 混合裁剪：生产环境的实际方案

实际生产环境中，没有人只用单一策略。混合裁剪（Hybrid Pruning）是将多种策略组合使用，对不同类型的消息采用不同的裁剪方法。

💡 混合裁剪的核心思想

不是"选一个策略"，而是"给每类消息分配最合适的策略"。就像垃圾回收——不是所有垃圾一锅端，而是分类处理：可回收的提取精华、有害的单独处理、厨余的堆肥压缩、其他的直接丢弃。

混合裁剪架构

混合裁剪实现

from dataclasses import dataclass
from enum import IntEnum

class Priority(IntEnum):
    SYSTEM = 0      # 永不裁剪
    SCHEMA = 1      # 尽量保留
    TOOL_RESULT = 2 # 可提取
    THOUGHT = 3     # 可摘要
    CHITCHAT = 4    # 可丢弃

@dataclass
class Message:
    role: str
    content: str
    msg_type: str          # system / user / assistant / tool
    priority: Priority
    tokens: int

class HybridContextManager:
    """混合裁剪上下文管理器"""

    def __init__(self, token_budget: int):
        self.token_budget = token_budget

    def prune(self, messages: list[Message]) -> list[Message]:
        total = sum(m.tokens for m in messages)
        if total <= self.token_budget:
            return messages

        # 第1阶段: 分类
        groups = {p: [] for p in Priority}
        for m in messages:
            groups[m.priority].append(m)

        # 第2阶段: 按优先级逐层处理
        budget = self.token_budget

        # P0: 全量保留，扣减预算
        p0_tokens = sum(m.tokens for m in groups[Priority.SYSTEM])
        budget -= p0_tokens

        # P4: 全部丢弃
        budget -= sum(m.tokens for m in groups[Priority.CHITCHAT])  # 释放

        # P3: 摘要压缩
        p3_compressed = []
        for m in groups[Priority.THOUGHT]:
            summary = self._summarize(m.content)
            m2 = Message(m.role, summary, m.msg_type, m.priority, len(summary)//4)
            p3_compressed.append(m2)
            budget -= m2.tokens
            if budget <= 0:
                break

        # P2: 提取关键字段
        p2_compressed = []
        for m in groups[Priority.TOOL_RESULT]:
            extracted = self._extract_key_fields(m.content)
            m2 = Message(m.role, extracted, m.msg_type, m.priority, len(extracted)//4)
            p2_compressed.append(m2)
            budget -= m2.tokens
            if budget <= 0:
                break

        # P1: 如果预算不够, 精简 Schema 描述
        p1_compressed = groups[Priority.SCHEMA]
        if budget < sum(m.tokens for m in p1_compressed):
            p1_compressed = [self._compress_schema(m) for m in p1_compressed]

        # 第3阶段: 按顺序重组
        return (groups[Priority.SYSTEM] +
                p1_compressed +
                p2_compressed +
                p3_compressed +
                [m for m in messages if m.priority == Priority.SYSTEM])
enum Priority {
  System = 0,       // 永不裁剪
  Schema = 1,       // 尽量保留
  ToolResult = 2,   // 可提取
  Thought = 3,      // 可摘要
  Chitchat = 4,     // 可丢弃
}

interface Message {
  role: string;
  content: string;
  msgType: string;
  priority: Priority;
  tokens: number;
}

class HybridContextManager {
  constructor(private tokenBudget: number) {}

  async prune(messages: Message[]): Promise {
    const total = messages.reduce((s, m) => s + m.tokens, 0);
    if (total <= this.tokenBudget) return messages;

    // 第1阶段: 分类
    const groups = new Map();
    for (const m of messages) {
      if (!groups.has(m.priority)) groups.set(m.priority, []);
      groups.get(m.priority)!.push(m);
    }

    let budget = this.tokenBudget;

    // P0: 全量保留
    budget -= this.sumTokens(groups, Priority.System);

    // P4: 全部丢弃（释放预算）
    budget += this.sumTokens(groups, Priority.Chitchat);

    // P3: 摘要压缩
    const p3 = (groups.get(Priority.Thought) || []).map(m => ({
      ...m, content: this.summarize(m.content), tokens: Math.floor(m.content.length / 16)
    }));
    budget -= p3.reduce((s, m) => s + m.tokens, 0);

    // P2: 提取关键字段
    const p2 = (groups.get(Priority.ToolResult) || []).map(m => ({
      ...m, content: this.extractKeyFields(m.content), tokens: Math.floor(m.content.length / 16)
    }));
    budget -= p2.reduce((s, m) => s + m.tokens, 0);

    // P1: 预算不够则精简 Schema
    let p1 = groups.get(Priority.Schema) || [];
    if (budget < p1.reduce((s, m) => s + m.tokens, 0)) {
      p1 = p1.map(m => ({ ...m, content: this.compressSchema(m.content), tokens: Math.floor(m.content.length / 8) }));
    }

    // 第3阶段: 按顺序重组
    return [...(groups.get(Priority.System) || []), ...p1, ...p2, ...p3];
  }

  private sumTokens(groups: Map, p: Priority): number {
    return (groups.get(p) || []).reduce((s, m) => s + m.tokens, 0);
  }

  private summarize(text: string): string { /* LLM 摘要 */ return text.slice(0, 200); }
  private extractKeyFields(text: string): string { /* 提取关键字段 */ return text.slice(0, 100); }
  private compressSchema(text: string): string { /* 精简描述 */ return text.slice(0, 150); }
}
📊 混合裁剪效果对比

一个 30 轮对话、原始 85,000 token 的上下文，经混合裁剪后：

  • P0（System + 当前输入）：2,500 token → 全保留
  • P1（工具 Schema）：3,000 token → 精简描述后 1,800 token
  • P2（工具返回值 ×15）：45,000 token → 提取关键后 4,500 token
  • P3（推理过程 ×15）：20,000 token → 摘要后 2,000 token
  • P4（寒暄 ×5）：2,500 token → 全丢弃
  • 总计：10,800 token（压缩率 87%）

5.5 上下文工程与记忆系统的关系

初学者常把"上下文工程"和"记忆系统"混为一谈。两者关系密切但关注点不同：

维度 上下文工程（本章） 记忆系统（第7章）
工作层短期 — 当前上下文窗口内长期 — 跨会话持久化
核心问题窗口装不下时怎么裁会话结束后怎么存
时间尺度单次会话内（分钟~小时）跨会话（天~月）
典型手段裁剪、压缩、优先级分级向量数据库、摘要持久化、KV 缓存
数据流向LLM ← 上下文窗口 ← 裁剪器LLM → 记忆写入 → 数据库 → 下次会话注入

两者协作的方式：记忆系统负责存什么（哪些经验值得跨会话保留），上下文工程负责带什么（这次调用 LLM 时，窗口里放什么）。记忆系统检索到的内容，会作为"记忆注入"消息进入上下文窗口，然后由上下文工程的裁剪策略决定是否保留。

5.6 工业级案例：Claude Code 的三级压缩链

Claude Code 是目前上下文工程做得最精细的 Agent 产品之一。它实现了三级压缩链，在对话不断增长的过程中自动触发：

🏭 Claude Code 三级压缩链

Claude Code 源码（src/compact/ 目录，12 个文件 3972 行）实现了完整的上下文管理系统：

第1级：microCompact — 微压缩

触发时机：每轮对话后自动执行，当前上下文接近 70% 容量时。

做法：扫描对话历史中的工具返回值，将大块输出替换为摘要。例如 8000 行的 read_file 输出，压缩为"文件 app.py，共 800 行，主要函数：main()、process()、validate()"。

// microCompact 伪代码
function microCompact(messages) {
  for (msg of messages) {
    if (msg.type === 'tool_result' && msg.tokens > 500) {
      msg.content = summarizeToolResult(msg.content)
      // 8000 token → 200 token
    }
  }
  return messages
}
  • 压缩率：约 30-40%
  • 信息损失：低，只压缩工具返回值的冗余部分
  • 额外开销：小，用规则提取而非 LLM 摘要

第2级：autoCompact — 自动摘要压缩

触发时机：当 microCompact 后仍接近 85% 容量时自动触发。

做法：用 LLM 对整个对话历史生成结构化摘要，然后用摘要替代旧消息，保留最近 N 轮完整对话。

// autoCompact 伪代码
function autoCompact(messages, recentN = 10) {
  // 1. 分割为"旧历史"和"近期对话"
  oldMessages = messages[:-recentN]
  recentMessages = messages[-recentN:]

  // 2. 对旧历史生成结构化摘要
  summary = llm.summarize(oldMessages, {
    preserveKeys: ['user_goals', 'decisions', 'constraints', 'tool_calls'],
    maxTokens: 2000
  })

  // 3. 保留 20,000 token 给摘要（p99.99 实测 17,387）
  return [summaryMessage, ...recentMessages]
}
  • 压缩率：约 60-70%
  • 信息损失：中，保留关键决策和约束，丢失推理细节
  • 额外开销：高，需要一次 LLM 调用生成摘要
⚠️ autoCompact 的防死锁设计

Claude Code 源码中有一个递归守卫 shouldAutoCompact：当查询来源是 'session_memory' 或 'compact' 时，返回 false，防止"压缩 → 查询 → 再压缩"的死循环。

另有 MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3 熔断机制——连续失败 3 次后停止自动压缩，避免无限重试。

第3级：sessionMemoryCompact — 会话记忆持久化

触发时机：用户手动执行 /compact 命令，或会话结束前。

做法：将整个会话的精华写入持久化记忆文件（CLAUDE.md），下次会话启动时自动加载。这已经不是"压缩"，而是"转存"——把短期记忆转为长期记忆。

// sessionMemoryCompact 伪代码
function sessionMemoryCompact(messages) {
  // 1. 提取值得长期保留的内容
  memory = llm.extract(messages, {
    types: ['user_preference', 'project_context', 'feedback', 'reference'],
    maxTokens: 25000,  // MAX_ENTRYPOINT_BYTES
    maxLines: 200      // MAX_ENTRYPOINT_LINES
  })

  // 2. 写入持久化记忆文件
  fs.writeFile('CLAUDE.md', memory.toMarkdown())

  // 3. 下次会话启动时自动加载
  // → 作为 System Prompt 的一部分注入上下文
}
  • 压缩率：极高，整个会话 → 一个文件
  • 信息损失：高，只保留四类记忆（user/feedback/project/reference）
  • 额外开销：高，但只在会话结束时执行一次

三级压缩链全景

级别 触发时机 做什么 压缩率 信息损失
microCompact~70% 自动压缩工具返回值30-40%低
autoCompact~85% 自动LLM 摘要旧历史60-70%中

💡 设计哲学

Claude Code 三级压缩链体现了一个重要设计哲学：压缩不是一次性操作，而是渐进式的。先用低成本方法压缩低价值内容，不够再用中成本方法压缩中价值内容，最后用高成本方法转存高价值内容。就像水坝泄洪——先开小闸，不够再开中闸，最后才开大闸。

面试高频题
Q1: 上下文工程和提示词工程有什么区别？
提示词工程关注单条指令怎么写（Few-shot、CoT、角色设定），上下文工程关注每次调用时上下文窗口里放什么（裁剪、压缩、优先级分级）。前者时间跨度是一轮对话，后者是整个会话生命周期。两者互补：好的提示词让单轮更有效，好的上下文工程让多轮可持续。在 Agent 跑 30 轮后，上下文工程的重要性超过提示词工程——因为关键约束有没有被裁掉决定了 Agent 是否还能正常工作。
Q2: 五种消息裁剪策略分别是什么？各自的压缩率和信息保留如何？
① 截断：超限时直接丢弃最早消息，压缩率高但信息保留差。② 摘要压缩：用 LLM 生成旧对话摘要，压缩率中高、信息保留中等，但消耗额外 token。③ 滑动窗口：保留最近 N 轮，上下文长度恒定，但不考虑重要性。④ 选择性保留：按消息类型分别处理（System 全留、工具结果提取、闲聊丢弃），信息密度最高。⑤ 语义保护型：锁定核心指令、保留行动-结果对、只压缩中间推理，压缩率和信息保留最优，但实现最复杂。
Q3: 什么是混合裁剪？为什么生产环境不使用单一策略？
混合裁剪是给每类消息分配最合适的裁剪策略：P0（System/当前输入）全量保留、P1（Schema/用户约束）尽量保留、P2（工具返回值）提取关键字段、P3（推理过程）摘要压缩、P4（闲聊）直接丢弃。生产环境不用单一策略是因为：截断会丢关键约束、摘要压缩成本高且慢、滑动窗口不区分重要性。混合裁剪兼顾压缩率和信息保留率，就像垃圾分类处理——不同类型用不同方法，效果最优。
Q4: Claude Code 的三级压缩链是什么？各级的触发时机和压缩方式有何不同？
① microCompact（~70% 触发）：压缩工具返回值的大块输出为摘要，规则提取而非 LLM，压缩率 30-40%，信息损失低。② autoCompact（~85% 触发）：用 LLM 对旧历史生成结构化摘要，保留最近 N 轮完整对话，压缩率 60-70%，信息损失中等。有防死锁递归守卫和 3 次连续失败熔断。③ sessionMemoryCompact（手动/会话结束触发）：将整个会话精华写入 CLAUDE.md 持久化，下次会话自动加载，压缩率 >90%，只保留四类记忆（user/feedback/project/reference）。设计哲学是"渐进式压缩"——先低成本压低价值内容，不够再中成本压中价值，最后高成本转存高价值。
Q5: 上下文工程和记忆系统有什么关系和区别？
工作层不同：上下文工程是短期（单次会话内窗口管理），记忆系统是长期（跨会话持久化）。核心问题不同：上下文工程解决"窗口装不下时怎么裁"，记忆系统解决"会话结束后怎么存"。协作方式：记忆系统检索到的内容作为"记忆注入"进入上下文窗口，上下文工程的裁剪策略决定是否保留这些注入内容。记忆系统负责"存什么"，上下文工程负责"带什么"。
Q6: 消息优先级裁剪的 P0-P4 分级是什么？裁剪时的执行顺序是什么？
P0（永不裁剪）：System Prompt、当前用户输入。P1（尽量保留）：工具 Schema、用户初始约束。P2（可压缩）：工具返回值、Action-Observation 对。P3（可摘要）：中间推理过程。P4（可丢弃）：寒暄、确认、重复消息。裁剪执行顺序是从低优先级到高优先级：先丢 P4 → 不够再摘要 P3 → 不够再提取 P2 → 不够再精简 P1 → P0 永不动。这保证了关键信息最后才受影响。
