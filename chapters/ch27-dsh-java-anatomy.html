第11章 工业级 Harness 解剖：deepseek-harness-java

把一个 878 个类的 Java Agent 运行时拆开看——教科书没写的生产级设计

11.1 为什么要解剖一个真实工程？

前一章讲了 Harness 的六大组件和设计原则。但看过原则不等于会写——就像背过设计模式不等于能搭出一个能扛流量的系统。这一章我们换一个学法：把一个真实的、生产级的 Agent Harness 工程拆开，看它的骨架怎么搭、关节怎么连、防线怎么设。

解剖对象是 deepseek-harness-java（简称 DSH Java）：一个 Java 17 + Spring Boot 3 的 Agent 运行时基座，约 878 个 Java 文件，DDD 六边形架构，事件溯源会话存储，支持 MCP、Skills、插件、子智能体、审批门禁、多协议 LLM 接入——基本上是 Claude Code 那套能力模型在 Java 技术栈上的完整实现。

🎯 本章的学习方法

每节按同一个节奏展开：问题 → 教科书做法 → 生产级做法 → 源码证据。重点不是记住类名，而是理解"为什么教科书做法在生产环境会翻车"。所有代码均来自工程真实源码（包名 cn.xiaofuge.deepseek.harness），有删减但语义未改。

11.2 整体架构：DDD 六边形 + 组合根

DSH Java 是 Maven 多模块工程，依赖方向严格单向：trigger → case → domain ← infrastructure，最外层由 app 模块装配启动。这不是教科书里"controller-service-dao 三层"的平铺结构，而是六边形架构（Hexagonal Architecture）：领域在中心，外部世界通过"端口（Port）"和"适配器（Adapter）"与领域通信。

11.2.1 domain 层：20+ 个子域，每个都是完整的六边形

domain 模块有 404 个类，按子域划分：agent、llm、tool、skill、plugin、session、hooks、guard、sandbox、workflow、goal、plan、todo、jobs、schedule、lsp、mcp、acp、e2b、subagent……每个子域内部再分三层：

📦 model（领域模型）

entity / valobj / aggregate。比如 SessionLog（会话事件日志实体）、TurnEndReason（回合结束原因值对象，sealed 类型：Completed / MaxTokens / Blocked / Aborted / Error）。

🔌 adapter/port（端口）

对外的依赖全部抽象成接口。比如 ILlmRuntimePort（调 LLM）、IFsPort（读写文件）、IShellExecutor（执行命令）、IPermissionMatrixPort（权限矩阵）。领域层只认识接口，不认识任何具体实现。

⚙️ service（领域服务）

真正的业务逻辑。ReactLoopAgent（核心驱动器）、BasicCompactionEngine（压缩引擎）、DangerousCommandGuard（危险命令守卫）都在这层。

💡 为什么领域层要"零框架依赖"？

因为框架是会换的，业务规则是沉淀的。domain 不 import Spring，意味着这套 Agent 核心逻辑可以原封不动地搬到 Quarkus、搬到命令行应用、甚至搬到 Android。上一章说过"变量是 Harness"——Harness 里最值钱的资产就是领域逻辑，它必须不依赖任何会过时的东西。

11.2.2 组合根：所有依赖在一个地方装配

六边形架构的关键问题是：谁在什么时候把接口和实现接上？答案是"组合根（Composition Root）"——AgentRunBeanConfig，全工程唯一的装配中枢：

// infrastructure/config/AgentRunBeanConfig.java —— 全工程的装配中枢
@Configuration
public class AgentRunBeanConfig {

    @Bean
    public CompactionEngine compactionEngine(
            LlmGenerationService llmGenerationService,
            // 配置直注：压缩阈值 100K token，最少保留 6 条消息
            @Value("${harness.agent.compaction.pressure-threshold-tokens:100000}") long threshold,
            @Value("${harness.agent.compaction.min-messages-to-compact:6}") int minMessages) {
        return new BasicCompactionEngine(llmGenerationService, threshold, minMessages);
    }

    // ……LLM 端口、工具注册表、审批网关、沙箱执行器、子智能体注册表……
    // 最终全部汇入 AgentRunFactory，工厂按会话创建 ReactLoopAgent 实例
}

这个设计的实战价值在于：换实现只改一处。想把 JSONL 会话存储换成 MySQL？把 JsonlSessionEventStore 的 Bean 换成 JdbcSessionEventStore 就行，领域层一行不动。想接一个新的 LLM 渠道？注册一个新 Adapter。这就是为什么这个工程能同时支持 DeepSeek / OpenAI 兼容 / Anthropic 三种协议、H2 / MySQL 两种存储。

11.3 事件溯源会话模型：不存消息，存事件

教科书做法：会话就是一个 List<Message>，每轮对话往里 append，持久化就是把 List 序列化成 JSON。这个做法在 Demo 里没问题，但在生产环境会踩三个坑：

❌ 坑 1：崩溃即丢失

整份 JSON 定期全量写盘，两次写盘之间崩溃，中间几轮对话就没了。而且文件越大写越慢。

❌ 坑 2：中间状态不可见

List 里只有"消息"，丢了大量过程信息：第几轮 turn、第几步 step、工具调用的耗时、token 用量、审批记录……出问题时无法复盘。

❌ 坑 3：并发写互相覆盖

两个实例同时打开同一个会话文件，后写的把先写的覆盖掉，谁也发现不了。

DSH Java 的解法是数据库领域的经典思想——事件溯源（Event Sourcing）：不存"当前状态"，存"发生的所有事情"。会话状态是事件流折叠出来的视图。

11.3.1 SessionEvent：二十余种事件类型

会话期间发生的一切都落成事件：turn/start、turn/end、step/start、step/end、user/message、assistant/chunk（流式增量）、assistant/message、tool/call、tool/result、request/header（请求元数据）、plan/mode……每个事件带一个单调递增、无空洞的序列号 seq。

// domain/session/event/model/entity/SessionLog.java
// 单个会话的内存有序事件日志，承担 WAL（预写日志）缓冲职责
public class SessionLog {
    private final String sessionId;
    private final SessionHeader header;
    private final List<SessionEvent> events = new ArrayList<>();
    private long nextSeq = 0;

    // 追加事件并分配顺序序列号（线程安全）
    public synchronized SessionEvent append(SessionEvent event) {
        SessionEvent withSeq = reassignSeq(event, nextSeq);
        events.add(withSeq);
        nextSeq++;
        return withSeq;
    }
}

11.3.2 消息历史是"折叠出来的"

要调 LLM 时，通过 deriveMessages() 从事件流折叠出消息历史；要展示前端视图时，用 SurfaceProjector 做投影；进程重启后，SessionRebuilderService 重放事件就能精确重建会话到任意一个历史时刻——这就是事件溯源的免费午餐：完整的审计能力、任意时间点回放、天然的调试工具。

💡 两个容易被忽略的细节

① 事件类型带 ignorable 标记：assistant/chunk（流式增量）回放时可以跳过，只有最终的 assistant/message 才影响状态——重建又快又准。
② 写租约：SessionWriteLeaseService 保证同一会话同一时刻只有一个实例在写，冲突直接抛 SessionWriteLeaseConflictException，把"并发覆盖"从静默事故变成显式异常。

11.4 生产级 Agent Loop：Inbox 驱动的双层循环

第 6 章的 ReAct 循环是这样的：while (turns < max) { 调LLM → 有工具调用就执行 → 否则返回 }。这个模型有一个隐含假设：用户发完一条消息就安静等着。但真实产品是——Agent 跑到一半，用户又插了一句"顺便把 README 也改了"；或者用户点了"停止"；或者系统需要在空闲时做上下文压缩。教科书循环处理不了这些情况。

DSH Java 的核心驱动器 ReactLoopAgent 用了三个教科书里没有的结构：

11.4.1 Inbox：消息先进收件箱，再谈执行

用户消息不直接触发循环，而是进入 Inbox，并标记目标是 CURRENT_TURN（当前回合消费）还是 NEXT_TURN（下一回合再处理）。然后 wakeDriver() 唤醒驱动器。这个解耦带来一个关键能力：用户中途插话——Agent 正在跑 turn 时新消息进来排队，当前 step 结束后被自然消费，而不是丢失或打断。

// domain/agent/service/run/ReactLoopAgent.java（精简）
public synchronized void send(Message message, InboxTarget target, boolean wakeup) {
    if (phase instanceof Phase.Running r && r.abort().get()) {
        // 正在取消中：wakeup 消息改排到 NEXT_TURN，避免与当前回合收尾竞争
        target = InboxTarget.NEXT_TURN;
    }
    inbox.append(target, message);
    if (wakeup) wakeDriver(false);
}

11.4.2 Phase 状态机：Idle / Running / Maintenance

Agent 不是"在跑/没跑"两个状态，而是 sealed 三态：Phase.Idle（空闲）、Phase.Running（执行中）、Phase.Maintenance（维护中）。Maintenance 是精髓：空闲期执行压缩、重建等维护任务时，Agent 显式处于"维护态"——这期间进来的消息不会触发并发执行，而是记一个 wakeRequested 标记，维护结束后统一重放。没有这个状态，"压缩跑到一半用户发消息"就是竞态 Bug 的重灾区。

11.4.3 turn / step 双层循环与终止条件

外层是 turn 循环（消费 Inbox 直到清空），内层是 step 循环（一轮 turn 内的"调 LLM → 执行工具 → 回填"迭代）。终止条件设计得非常全：

终止原因（TurnEndReason） 触发条件 处理策略
Completed模型不再请求工具正常结束本 turn
MaxTokens输出被 token 上限截断受控续写：注入续写提示让模型从断点接着写，最多 4 次
步数上限单 turn 达 50 步强制结束，记 Error("MAX_STEPS")
Aborted用户取消原子 abort 标记，在安全点（step 边界）停止
Blocked / Error被阻塞 / 异常落 turn/end 事件，出错时若 assistant 消息为空则合成可见错误消息，避免前端白屏
🔥 MaxTokens 受控续写——教科书完全不讲的高频坑

模型写长代码/长文档时，输出经常撞上 max_tokens 被截断。教科书做法：用户看到半截代码，自己说一句"继续"。生产做法：Harness 检测到 finish_reason=length 后，自动注入续写提示（"从断点继续输出"），把多次续写的片段拼接成完整输出，最多续 4 次防止失控。用户根本感知不到截断发生过。

11.5 安全双防线：审批门禁 + 危险命令守卫

第 24 章讲过 Agent 权限控制。DSH Java 把"能不能执行"拆成了两道独立的防线，工程注释里有一句话把两者的关系讲得淋漓尽致：

🛡️ 双防线的本质

审批是"谁来放行"，守卫是"永远不放行"。

审批解决的是"这个操作需要人确认"（写文件、跑命令）；守卫解决的是"这个操作任何人都不该批准"（rm -rf /、fork 炸弹、curl|sh 管道）。人会被骗、会手滑、会疲劳审批——所以必须有一道人点"同意"也过不去的防线。

11.5.1 审批门禁：四态裁决 + 挂起等待

RuntimeApprovalGate 在每次工具派发前裁决。注意它的设计细节：

// domain/tool/service/RuntimeApprovalGate.java（精简）
@FunctionalInterface
public interface RuntimeApprovalGate {

    enum Decision { ALLOW, DENY }

    Decision check(String toolName, Object arguments);

    /** 预判：随后调用 check 会阻塞等待人工裁决吗？
     *  供执行器在挂起前向 SSE 发出 requires_approval 信号，
     *  让前端显示"等待审批"而不是误显示"工具执行中"。 */
    default boolean requiresApproval(String toolName) { return false; }

    /** 人工裁决入口：默认拒绝（防御性编程），装配层注入阻塞等待实现 */
    default ApprovalVerdict ask(ApprovalRequest request) { return ApprovalVerdict.DENY; }

    /** 四态裁决：放行一次 / 本会话放行该工具 / 拒绝 / 取消整个任务 */
    enum ApprovalVerdict { ALLOW_ONCE, ALLOW_SESSION, DENY, CANCEL }
}

三个值得抄的设计：

① ALLOW_SESSION：会话级记忆

用户批准过一次 fs_write，可以选择"本会话内都放行"，不用每写一次文件点一次确认。裁决粒度是"操作类型 × 会话"，不是简单的"是/否"。

② requiresApproval 预判信号

阻塞挂起（默认超时 600s）之前先通知前端"我要挂起了"。没有这个信号，前端会把审批等待误渲染成"工具执行中"，用户以为卡死了。

③ 跨实例审批聚合

AggregatingRuntimeApprovalGateway 把远端数字人端点的待决审批也聚合进来——多个 Agent 实例的审批请求在一个界面里统一裁决。分布式 Agent 系统的真实需求。

11.5.2 危险命令守卫：正则拦截"永远不放行"的命令

DangerousCommandGuard 是审批之外的第二道防线，内置正则拦截：递归强删根目录（含选项乱序和变量展开的变体）、写块设备（dd/mkfs/fdisk）、fork 炸弹、关机重启、覆写系统目录、chmod 递归打根、curl|sh 管道远程脚本……还支持 harness.shell.blocked-patterns 配置追加。

// domain/tool/shell/DangerousCommandGuard.java（节选）
private static final List<Pattern> BUILTIN = List.of(
    // 递归/强制删除根或家目录（含变量展开与选项乱序）
    Pattern.compile("\\brm\\b[^\\n;|]*-[a-zA-Z]*[rRf][a-zA-Z]*[fF]?[^\\n;|]*\\s+(/|/\\*|~|\\$HOME)(\\s|$)"),
    // fork 炸弹  :(){ :|:& };:
    Pattern.compile(":\\s*\\(\\s*\\)\\s*\\{[^}]*:\\s*\\|\\s*:"),
    // curl|sh 管道远程脚本
    Pattern.compile("\\b(curl|wget)\\b[^\\n|]*\\|\\s*(sudo\\s+)?(ba|z|fi)?sh\\b"),
    // ……写块设备、关机重启、覆写 /etc /boot 等
);
💡 防线设计的一般原则

注意 check() 的返回值设计：放行返回 null，拦截返回人类可读的拦截原因。原因会回填给模型——模型知道"为什么被拦"，就能换个安全的做法重试，而不是一脸懵地重复同一个命令。安全机制的反馈对象不只是人，还有模型。

11.6 ArchUnit：把架构约束写成测试

"domain 层不能依赖 infrastructure"、"领域代码不能用 Spring 注解"——这类约定几乎每个项目立项时都写过，然后随着时间推移被一个又一个"就这一次"的 PR 击穿。DSH Java 的做法是：把架构规则变成单元测试，违反就编译不过（CI 红）。

// domain 模块测试：AgentRunArchitectureTest.java（完整，就这么短）
class AgentRunArchitectureTest {

    @Test
    void domainMustNotDependOnInfrastructure() {
        var classes = new ClassFileImporter()
                .withImportOption(new ImportOption.DoNotIncludeTests())
                .importPackages("cn.xiaofuge.deepseek.harness");

        ArchRuleDefinition.noClasses()
                .that().resideInAPackage("..domain..")
                .should().dependOnClassesThat()
                .resideInAnyPackage("..infrastructure..")
                .check(classes);
    }

    @Test
    void agentDomainMustNotDependOnSpring() {
        // domain.agent 包下的类不允许依赖 org.springframework 的任何类
        ArchRuleDefinition.noClasses()
                .should().dependOnClassesThat()
                .resideInAnyPackage("org.springframework..")
                .check(classes);
    }

    @Test
    void agentDomainMustNotDependOnJackson() {
        // 连序列化框架都不许碰——领域模型怎么序列化是基础设施层的事
        ArchRuleDefinition.noClasses()
                .should().dependOnClassesThat()
                .resideInAnyPackage("com.fasterxml..")
                .check(classes);
    }
}

这就是"架构即代码（Architecture as Code）"。它的意义在于把架构约束从靠 Reviewer 的记忆和自觉变成靠 CI 强制：新人不知道分层规则？没关系，写错了测试会告诉他。这个工程四个模块各有一套架构测试（domain/api/trigger/case），36 个测试类里最有价值的恰恰是这几个"什么都不测业务逻辑"的测试。

✅ 什么时候值得引入 ArchUnit

判断标准很简单：你的项目会活过三个月，且会有第二个人提交代码。一次性 Demo 不需要；打算长期演进的 Agent 基座，早引入早受益——架构腐化是渐进的，等发现时已经积重难返。

11.7 Skills 的工程化：rank 覆盖与工具化加载

第 15 章讲过 Skills 的渐进式披露。DSH Java 把它落到了三个具体的工程机制上：

11.7.1 多来源扫描 + rank 覆盖

Skills 不只有一个目录。FilesystemSkillProviderPort 按 rank 扫描多个根：项目级 .dsh 目录（rank 100）< 自定义 roots（300）< 用户 home（400）< 内置 bundled（600）。同名 skill，低 rank 胜出——项目里的 skill 可以覆盖全局同名 skill。这和 Git 的 local 覆盖 global、CSS 的就近原则如出一辙：越靠近当前工作现场的配置，优先级越高。

11.7.2 系统提示词只放摘要，正文按需加载

系统提示词里只注入每个 skill 的 name + description + when_to_use（YAML frontmatter 里的摘要），几十个 skill 也就几百 token。模型判断需要某个 skill 时，主动调用 skill 工具，完整正文作为工具结果返回，注入后续步骤的上下文。另外支持运行期热停用（setDisabledNames）和从 Git 仓库安装——skill 的完整生命周期都在运行期可控。

11.7.3 插件不止加工具，还能改系统提示词

插件（Java URLClassLoader 隔离加载，或 Node 进程 JSON-RPC 桥接）通过 SpringPluginContext 拿到宿主能力，其中一个关键能力是向 ScopedSystemPromptAssembler 注册 prompt section——插件可以改写 Agent 的"人设"。比如装一个"数据库运维插件"，不只是多了几个 SQL 工具，Agent 的系统提示词里还会多出一段"你是数据库运维专家，遵循以下安全规范……"。工具是手，提示词是脑——插件机制同时伸向两者，才是真正的扩展点设计。

11.8 子智能体的终局：把别的 CLI Agent 当工具调度

第 17 章讲过多 Agent 协作，教科书做法是"在同一个框架里再起一个 Agent 实例"。DSH Java 的子智能体体系分两层：

进程内子智能体

SpawnInProcessProvider / ForkInProcessProvider：子 Agent 在独立 session、独立上下文运行，只把最终结论回填父会话。隔离的价值：子任务的几十步中间推理不会污染父会话的上下文窗口。

外部 CLI 子智能体（罕见设计）

ClaudeCodeSubagentProvider / CodexSubagentProvider / AcpSubagentProvider：把 claude、codex 这些别人家的 CLI Agent 当子 Agent 调度。你的 Harness 编排层在顶层，底层执行的可以是任何厂商的 Agent 产品。

🔥 这个设计为什么重要

它意味着 Agent 系统的编排层和执行层可以来自不同厂商。Claude Code 擅长写代码、Codex 擅长另一种任务、你自己的 Java Agent 擅长企业内部系统集成——Harness 层面的编排器可以把任务路由给最合适的执行体。这正是 A2A（Agent-to-Agent）协议想要标准化的未来：Agent 之间像微服务一样互相调用。DSH Java 已经实现了 A2A 协议的 Agent Card 端点和 ACP 域，是这个未来的早期形态。

11.9 生产级稳定性：那些教科书不讲的"小"机制

最后汇总几个散装但高频的生产机制。它们单看都不复杂，但缺了任何一个，Agent 在真实使用里都会周期性地出洋相：

机制 解决什么问题 实现要点
RepeatToolReminder
防打转提醒		 模型陷入死循环：反复调同一个工具、同样的参数，撞墙再撞墙 检测连续重复的工具调用模式，向上下文注入提醒消息（"你已经第三次尝试同样的调用，结果相同，请换思路"），把方向盘还给模型
工具超时熔断 工具挂死（网络分区、命令卡死），整个回合无限阻塞 单工具默认 300s 超时，记 TOOL_TIMEOUT 失败回填给模型——失败也是信息，模型可以决策重试或放弃
LLM 重试可视化 上游限流/抖动时，用户以为系统死了 退避重试的进度以 StreamChunk.Retry 实时推给前端（"正在重试 2/3"），最终失败的消息附"已重试 N 次"
错误消息合成 LLM 请求失败时 assistant 消息为空，前端白屏 失败时合成一条可见的错误消息补进事件流，前端永远有东西可渲染
压力压缩引擎 长会话撞上下文上限 估算 token 超 100K 阈值时，turn 开始处自动触发：调 LLM 把旧消息区间总结成摘要消息替换原文；失败只记日志不打断主流程
Hooks 系统 想在工具执行前后插入自定义检查（对齐 Claude Code hooks） 按 HookPoint（PRE/POST）+ 工具名 matcher 匹配，执行 shell 命令 hook，多 hook 输出合并
✅ 一句话总结

教科书 Agent 和工业级 Harness 的差距，不在任何单点技术上，而在对"失败模式"的穷举：消息会中途来、输出会被截断、工具会挂死、模型会打转、LLM 会抖动、用户会手滑、并发会冲突——每一个"会"都有一道对应的机制在兜底。把失败当常态设计，才是生产级。

📋 八股总结 — 面试高频考点
Q1: 什么是事件溯源（Event Sourcing）？为什么 Agent 会话适合用它？
事件溯源：不存"当前状态"，存"导致状态变化的所有事件"；当前状态由事件流折叠（fold/replay）得出。事件 append-only，带单调递增序列号。

Agent 会话的契合点：① 崩溃恢复——事件即 WAL，重放即可精确重建到任意时刻；② 天然审计——每次工具调用、每步推理、每次审批都留痕；③ 过程可见——turn/step 边界、token 用量、耗时都在事件里，Debug 不用猜；④ 投影灵活——消息历史、前端视图、计费数据都是同一事件流的不同投影。

面试加分项：提"写租约防并发覆盖"和"ignorable 事件标记加速回放"（流式 chunk 可跳过）。
Q2: 生产级 Agent Loop 和教科书 ReAct 循环的核心差异？
教科书循环假设"用户发一条消息然后安静等待"，生产环境必须处理并发与中断：
① Inbox 解耦：消息先进收件箱（分 CURRENT_TURN / NEXT_TURN），支持用户中途插话，执行与输入解耦
② 阶段状态机：Idle / Running / Maintenance 三态，维护期（压缩/重建）进来的消息延后重放，避免竞态
③ turn/step 双层循环：turn 消费用户消息，step 是 turn 内的"LLM→工具→回填"迭代
④ 完整的终止语义：Completed / MaxTokens（受控续写≤4次）/ 步数上限 / Aborted（安全点取消）/ Blocked / Error，每种都有明确处置
Q3: Agent 安全防线怎么设计？审批和守卫是什么关系？
一句话：审批是"谁来放行"，守卫是"永远不放行"。

审批门禁解决"需要人确认"的操作（写文件、跑命令）：四态裁决 ALLOW_ONCE / ALLOW_SESSION / DENY / CANCEL；阻塞挂起等人工裁决（带超时）；挂起前向流式调用方发 requires_approval 预判信号，避免前端把审批等待误显示为执行中。

危险命令守卫解决"任何人都不该批准"的操作：静态正则拦截 rm -rf /、dd 写块设备、fork 炸弹、curl|sh 管道等——因为人会手滑、会疲劳审批、会被社工。

细节加分项：拦截时返回人类可读原因回填给模型，让模型知道为什么被拦、换安全做法重试。
Q4: MaxTokens 截断怎么处理？什么是受控续写？
模型输出撞上 max_tokens 时 finish_reason=length，输出是半截。教科书做法是把截断暴露给用户（"你自己说继续"）。

受控续写：Harness 检测到截断后，自动注入续写提示（"从断点继续"），把多次输出拼接成完整结果，最多续 4 次防止失控循环。用户对截断无感知。

设计要点：续写次数必须有上限；续写提示要明确要求"从断点处继续"而非重新生成；拼接逻辑要注意代码块等结构化内容的完整性。
Q5: ArchUnit 架构守护是什么？为什么比口头约定可靠？
ArchUnit：用单元测试断言代码结构规则的 Java 库。比如"domain 包的类不允许依赖 infrastructure 包"、"领域层不允许 import Spring/Jackson"——违反则测试失败、CI 变红。

口头/文档约定的问题：依赖 Reviewer 的记忆和自觉，会被"就这一次"的 PR 逐步击穿，架构腐化是渐进的，发现时已积重难返。

架构即代码把约束从"人治"变"法治"：新人不需要知道规则，写错了测试会告诉他。这就是"让正确的做法容易，让错误的做法不能编译"。
Q6: Skills 的渐进式披露在工程上怎么实现？
三个机制：
① 摘要入 prompt：系统提示词只放每个 skill 的 name + description + when_to_use（YAML frontmatter），几十个 skill 也就几百 token
② 正文工具化加载：模型判断需要时主动调 skill 工具，完整正文作为工具结果注入后续上下文——token 按需付费
③ 多来源 rank 覆盖：项目级 < 自定义 < 用户级 < 内置，同名 skill 低 rank（离工作现场近的）胜出，项目可以覆盖全局

延伸：插件机制同理，但插件还能注册 prompt section 改写系统提示词——不只加"手"（工具），还能改"脑"（人设）。
Q7: 什么是外部 CLI 子智能体？这个设计意味着什么？
外部 CLI 子智能体：把其他厂商的 CLI Agent（claude、codex 等）作为子 Agent provider 调度——子 Agent 在独立进程、独立上下文运行，只回填结论。

意味着 Agent 系统的编排层和执行层可以来自不同厂商：你的 Harness 做顶层编排（权限、审批、上下文、审计），底层执行体按任务类型路由给最合适的 Agent 产品。这是 A2A 协议想要标准化的未来的早期形态——Agent 之间像微服务一样互相调用。

同时进程内子智能体也强调"独立 session 独立上下文"：子任务的几十步中间推理不污染父会话上下文窗口。
Q8: 工业级 Harness 和教科书 Agent 的本质差距是什么？
不在单点技术，而在对失败模式的穷举：
消息会中途来 → Inbox + 状态机；输出会被截断 → 受控续写；工具会挂死 → 超时熔断；模型会打转 → RepeatToolReminder；LLM 会抖动 → 重试可视化；用户会手滑 → 双防线；并发会冲突 → 写租约；上下文会爆 → 压力压缩。

答题结构建议：先给观点（"把失败当常态设计"），再按"输入/执行/输出/资源/并发"五个维度各举一例，最后落到可量化指标（步数上限 50、续写上限 4、审批超时 600s、压缩阈值 100K——生产系统每个数字都有出处）。
